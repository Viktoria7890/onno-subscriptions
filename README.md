# Сервис подписок на onno

Тестовое задание: учёт и управление подписками клиентов на тарифные планы, сделанное на
[onno-framework](https://github.com/onno-erp/onno-framework) **3.4.1**.

Таблицы БД, REST API, формы, списки и миграции схемы **не написаны руками**: их генерирует
onno из типизированной Java-метамодели (справочники, документы, регистры, перечисления).
Руками написаны только бизнес-логика (проведение, правила, автоподстановка, регламентное задание)
и описание интерфейса (`EntityView`, `Layout`, `Page`).

## Быстрый старт

Нужно: **JDK 21** (если его нет, Gradle скачает сам) и Docker (для PostgreSQL).

```bash
# 1. PostgreSQL
docker compose up -d postgres

# 2. Приложение
./gradlew bootRun
```

Откройте http://localhost:8080 и войдите одной из кнопок на экране входа:

| Роль | Логин / пароль | Что может |
|---|---|---|
| Администратор | `admin` / `admin` | всё, в том числе создавать и менять тарифы (цены, снятие с продажи) |
| Менеджер | `manager` / `manager` | клиенты, платежи, подписки, отмена, отчёты, дашборд; тарифы — только просмотр и выбор в подписке |

Регистрации нет: пользователи заданы в `application.yaml` (`onno.auth.users`). Выйти — меню аккаунта
внизу слева → «Выйти».

При первом запуске создаются демо-данные: тарифы, клиенты, платежи и подписки (отключается
переменной окружения `DEMO_DATA=false`).

**Без Docker** (H2 в файле `./data`):

```bash
./gradlew bootRun --args='--spring.profiles.active=h2'
```

**Всё в Docker** (приложение + PostgreSQL):

```bash
docker compose --profile app up --build
```

**Тесты:**

```bash
./gradlew test
```

## Как пользоваться

1. **Справочники → Тарифы.** Тариф = цена за период + длительность периода в днях + флаг «доступен для
   подключения». Снятый с продажи тариф не предлагается в пикере новой подписки.
2. **Справочники → Клиенты.** Наименование, статус, e-mail, телефон, дата регистрации.
3. **Продажи → Платежи.** Создайте платёж и нажмите **«Провести»**: деньги поступят на лицевой счёт.
4. **Продажи → Подписки.** Выберите клиента, добавьте строки (тариф + число периодов) и сохраните:
   цена, сумма строки, итог и дата окончания посчитаются сами. **«Провести»** спишет итог с лицевого счёта.
   Если денег не хватает, проведение отклоняется с сообщением, сколько доступно и сколько требуется.
5. **Отменить подписку** можно значком ⊘ в конце строки списка или
   пунктом «Отменить подписку» в меню «⋯» на форме. Откроется окно с обязательной причиной. Если подписка
   была проведена, движения сторнируются: деньги вернутся на счёт, выручка перестанет учитываться.
   После отмены с формы обновите страницу: открытая форма onno не перечитывает запись сама.
6. **Отчёты → Лицевые счета** показывает текущие остатки по клиентам; **Отчёты → Выручка по тарифам**
   показывает обороты в разрезе тариф × клиент.
7. **Дашборд** — показатели за выбранный период, диаграммы и последние документы.

Статусы «Активна» и «Истекла» выставляет регламентное задание (раз в час), а также сразу после
проведения. Принудительно пересчитать их можно кнопкой **«Обновить статусы»** над списком подписок.

## Модель

| Сущность | Тип onno | Ключевые поля |
|---|---|---|
| Клиент `Client` | `@Catalog` | статус, e-mail, телефон, дата регистрации |
| Тариф `Tariff` | `@Catalog` | цена за период, длительность периода (дн.), доступен для подключения |
| Платёж `Payment` | `@Document` | клиент, сумма, способ оплаты |
| Подписка `Subscription` | `@Document` | клиент, статус, дата начала/окончания, итог, причина отмены, строки |
| Строка подписки `SubscriptionLine` | `@TabularSection` | тариф, периодов, цена, дней, сумма |
| Статус подписки, статус клиента, способ оплаты | `@Enumeration` | цветные «пилюли» через `@EnumLabel` |
| Лицевые счета `AccountBalance` | `@AccumulationRegister(BALANCE)` | измерение: клиент; ресурс: сумма |
| Выручка по тарифам `TariffRevenue` | `@AccumulationRegister(TURNOVER)` | измерения: тариф, клиент; ресурсы: сумма, периодов |

### Проведение

| Документ | Лицевые счета | Выручка по тарифам |
|---|---|---|
| Платёж | приход `+сумма` | — |
| Подписка | расход `−итог` | приход по каждой строке (сумма, периодов) |
| Подписка в статусе «Отменена» | — | — |

### Бизнес-правила (`Validated` + `BusinessRule`)

- клиент обязателен;
- хотя бы одна строка, в каждой строке выбран тариф;
- число периодов больше нуля;
- тариф доступен для подключения (проверяется до проведения: если тариф позже снимут с продажи,
  уже оформленные подписки это не затронет);
- платёж: клиент обязателен, сумма больше нуля.

### Нехватка денег

Защита двухуровневая:

1. `Subscription.beforePost()` сверяет итог с остатком лицевого счёта и выдаёт понятное сообщение.
2. Регистр `AccountBalance` объявлен как BALANCE без `allowNegative`, поэтому движок проведения
   **атомарно** отклонит любое проведение (или распроведение платежа), после которого остаток уйдёт
   в минус. Это работает даже при гонке двух одновременных проведений.

### Автоподстановка

- Дата документа и дата начала: инициализаторы полей (видны уже на пустой форме) + `onFilling()`
  с null-guard'ами.
- `beforeWrite()` при **каждом** сохранении: цена строки из тарифа, `дней = длительность × периоды`,
  `сумма = цена × периоды`, итог, `дата окончания = дата начала + max(дней)`.
- У проведённой подписки цена «заморожена» (снимок на момент оформления), чтобы повторное сохранение,
  например сменой статуса, не расходилось с уже записанными движениями.

### Статусы

`Оформлена → Активна → Истекла`, а также `→ Отменена`. Срок действия — полуинтервал
`[дата начала, дата окончания)`. Регламентное задание `SubscriptionStatusJob`
(`@ScheduledJob(cron = "0 * * * *")` + `BackgroundTask`, исполняется через JobRunr) переводит
проведённые и не отменённые подписки по датам. Черновики и отменённые не трогает.

### Почему в хуках нет Spring-бинов

Хуки onno (`beforeWrite`, `rules`, `beforePost`) выполняются на объекте, созданном рефлексией, без DI.
Тарифы и остатки нужны хукам через маленький интерфейс `BillingLookup`: в приложении его реализует
Spring-бин `BillingLookupInstaller`, в unit-тестах подставляется фейк в памяти.

## Тесты и трассировка

- `SubscriptionDomainTest` — unit-тесты доменной логики без Spring и БД (пересчёт, правила,
  проверка средств, состав движений).
- `SubscriptionStatusResolveTest` — таблица переходов статусов по датам.
- `SubscriptionFlowIT` — сквозные сценарии на поднятом приложении (H2 в памяти): настоящая схема,
  проведение через `PostingService`, чтение остатков и оборотов из регистров, отмена, регламентное задание.
- `TraceabilityTest` — проверяет, что каждое требование ТЗ (R1–R15) покрыто хотя бы одним тестом.
  Матрица «требование → код → тесты» — в [TRACEABILITY.md](TRACEABILITY.md).

## Структура

```
src/main/java/com/example/subscriptions
├── domain
│   ├── catalogs      Client, Tariff
│   ├── documents     Payment, Subscription, SubscriptionLine, SubscriptionRules
│   ├── enums         SubscriptionStatus, ClientStatus, PaymentMethod
│   ├── registers     AccountBalance, TariffRevenue
│   └── BillingLookup мост от доменных хуков к репозиториям
├── repository        типизированные репозитории onno
├── service           статусы, отмена, реакция на проведение, BillingLookupInstaller
├── jobs              SubscriptionStatusJob (@ScheduledJob)
├── seed              демо-данные
└── ui                MainLayout, DashboardPage, EntityView для каждой сущности
```
